Loss 분류 체계와 파레토

무엇을 먼저 고칠지 고르는 막대그래프는, 사건에 어떤 이름을 붙였느냐에 따라 1위가 바뀝니다

← 실험실 목록← 이전: 에이전트 평가

매주 Loss 보고에서 ‘무엇을 먼저 고칠까’를 고르는 도구가 파레토 그림입니다. 그런데 그 그림은 사건마다 붙인 이름(사유 코드)이 어떻게 설계되었느냐에 따라 1위가 전혀 다른 것이 됩니다. 이 실험실은 같은 가상 공장 일의 Loss 기록 건(잃은 유리 장)을 두 가지 이름으로 각각 그려 순위가 뒤바뀌는 것을 보고, 사유 코드를 합치고 나누면 그림이 어떻게 달라지는지 만져 보고, 기간과 시드를 바꿔 한 달 파레토의 1위가 우연으로도 바뀌는 정도를 잽니다. 마지막에 다음 달 개선 과제 하나를 숫자로 고릅니다.

시작하기 전에

이미 아시는 것 — 0206 의 상태·전이와 Loss 사건을 만든 시뮬레이터(simulateLoss), 0400 의 파이프라인과 실행 기록, 0402 의 평가 단위와 구간, 블록 한 곳이 챔버 4개로 4대·3대 운전을 한다는 것(0206), 막대그래프와 누적 비율.

  • 상태·전이·Loss 사건 (0206)
  • 파이프라인·실행 기록 (0400)
  • 평가 단위·구간 (0402)
  • 블록·챔버·4대/3대 운전 (0206)
  • 막대그래프·누적 비율

새로 이름을 붙이는 낱말은 여섯 개입니다. 쓰이는 자리에서 하나씩 정의하고, 정의한 뜻 그대로만 씁니다.

  • Loss
  • 사유 코드 (reason code)
  • 파레토 (Pareto chart)
  • 직접 사유 (direct reason)
  • 근본 원인 (root cause)
  • 순위 흔들림 (rank instability)

이 실험실에서 가져가는 것

  1. 실무에서 쓰는 곳 — 매주 Loss 보고에서 개선 과제를 고르는 파레토, 그리고 그 파레토가 기대는 사유 코드 체계의 설계(1~8절).
  2. 손으로 연습 — 같은 기록을 직접 사유와 근본 원인으로 각각 그려 순위가 뒤바뀌는 것 보기, 코드를 합치고 나누며 그림이 달라지는 것 보기, 주 단위와 시드를 바꿔 순위가 얼마나 흔들리는지 보기(4·6·7절).
  3. 다음 날 산출물 — pareto·merge_codes·rank_stability 등 Python 함수(10절), 주간 Loss 보고 양식과 사유 코드 설계 점검표(11절).
  4. 기록할 데이터 — 사건마다 직접 사유·근본 원인·원인 블록·시작과 끝·잃은 장수·사유를 붙인 사람이나 규칙과 시각, 그리고 코드 체계의 판(11절).
  5. 사람·규칙·에이전트의 몫 — 과제 선택과 코드 체계 승인은 사람, 사유를 붙이는 규칙과 재귀속은 규칙, 집계·파레토·순위 흔들림·보고 초안은 에이전트(8절).
  6. 성과 환산 — 증상에 과제를 걸었을 때와 근본 원인에 걸었을 때 고칠 수 있는 유리 장수와 챔버 턴 수(9절).

1절에서 지금 보고서의 파레토가 어디서 막히는지 확인하고, 3~6절에서 다시 그리는 법을 만들고, 7절에서 순위의 흔들림을 재고, 8절에서 이 물음으로 돌아옵니다. 개선율은 현장 값으로 바꿔야 할 가정입니다(9절).

여기서부터 가상 공장의 Loss 기록으로 푸는 풀이입니다

1첫 시도 — 지금의 보고서에 있는 파레토

  • Loss — 설비가 유리를 만들 수 있었는데 만들지 못한 몫입니다. 여기서는 잃은 유리 장수(loss_glass)와 잃은 챔버 분(loss_chamber_min) 두 가지로 잽니다. 챔버 한 곳이 1분 서면 챔버 1분을 잃은 것이고, 이를 한 장 만드는 데 걸리는 시간(분)으로 나누면 잃은 유리 장수가 됩니다.
  • 사유 코드 (reason code) — Loss 사건 하나에 붙이는 분류 이름입니다. 코드 체계는 코드의 목록과 그 코드를 붙이는 규칙을 합친 말입니다. 현장의 기록은 보통 사건마다 이름 하나를 붙입니다.
  • 파레토 (Pareto chart) — 사유 코드별 Loss 를 큰 순서로 늘어놓은 막대에 누적 비율의 선을 겹친 그림입니다. 앞의 몇 개 막대가 전체의 대부분을 차지하는지 보고, 그 막대를 개선 과제로 삼습니다.
파레토의 두 숫자 — 막대의 몫과 누적 비율 si=Li∑jLjCi=∑j=1isj L(i)는 큰 순서로 i번째 사유 코드의 Loss(유리 장수나 챔버 분), s(i)는 그 몫, C(i)는 1위부터 i위까지 더한 누적 비율입니다. 누적 비율이 80% 에 닿는 막대까지가 ‘앞의 몇 개’입니다.

가상 공장 일의 Loss 사건 건에는 사건마다 사유 코드가 하나씩 붙어 있습니다. 코드 체계는 시뮬레이터의 코드 개이고, 코드의 뜻은 아래 3절의 표에 있습니다. 이 기록을 지금 보고서의 방식대로 사유 코드별로 모아 파레토를 그립니다. 막대의 높이를 잃은 유리 장수로 볼지 챔버 분으로 볼지 골라 보십시오.

사유 코드별 Loss 파레토 — 지금 보고서의 그림
1위 막대그 밖의 막대누적 비율(오른쪽 축)

막힘. 1위는 압도적입니다. 그런데 1위 막대 ()를 개선 과제로 받은 사람은 무엇을 고쳐야 합니까. 이 코드의 뜻을 보면 ‘다른 블록의 사정 때문에 굶거나 막혔다’는 것이라 그 자체는 고칠 대상이 아닙니다. 다음 절에서 이 막대의 사건들을 열어 봅니다.

2막힘 — 1위 막대를 열어 보면 이유가 없습니다

1위 사유 코드 의 사건 건 가운데 잃은 장수가 큰 다섯 건을 보고서에 있는 그대로 펼친 것입니다. 보고서에 있는 칸은 사건·블록·시작·끝·사유 코드·잃은 장수가 전부입니다.

이 표로는 ‘그 블록은 왜 굶었는가’를 알 수 없습니다. 블록이 그 시간 동안 일을 못 한 것은 사실이지만, 어느 블록의 무슨 일 때문인지는 사유 칸이 말해 주지 않습니다. 그래서 막대 하나로는 과제를 만들 수 없고, 사건마다 ‘그 멈춤을 처음 일으킨 일’을 따로 적어야 합니다. 이름을 붙입니다.

3이름 — 직접 사유와 근본 원인

  • 직접 사유 (direct reason) — 그 자리에서 눈에 보이는 멈춘 이유입니다. 지금까지 본 사유 코드가 바로 직접 사유입니다. 예를 들어 앞 블록이 유리를 안 줘서 굶었다면 직접 사유는 입니다.
  • 근본 원인 (root cause) — 그 멈춤을 처음 일으킨 사건의 코드입니다. 직접 사유에서 거슬러 올라가 붙이며, 그 사건이 일어난 블록(원인 블록)도 함께 적습니다. 예를 들어 앞 블록의 한 챔버가 ()로 멈춰 뒤 블록이 굶었다면 근본 원인은 이고 원인 블록은 그 챔버가 있는 블록입니다.

기록에는 사유 말고 두 칸이 더 있었습니다. 직접 사유가 ‘무엇이 보였나’의 기록이라면 근본 원인과 원인 블록은 ‘무엇을 고쳐야 하나’의 기록입니다. 2절에서 본 가장 큰 사건에 이 두 칸을 채워 시간 축에 놓습니다. 사건을 고르는 규칙은 ‘ 사건 가운데 잃은 장수가 가장 큰 것 하나와, 그 사건의 원인 블록에서 같은 시간에 일어난 근본 사건들’입니다.

대표 사건 하나의 연쇄 — 근본 사건이 먼저, 굶음이 뒤따릅니다

규칙으로 거슬러 올라갈 수 있는 것은 규칙이 붙이고, 그럴 수 없는 것만 사람이 붙입니다. 앞 블록의 챔버가 PM 으로 서 있는 동안 뒤 블록이 굶었다는 사실은 두 사건의 시각과 블록 순서만으로 찾을 수 있습니다. 이런 연쇄는 규칙이 붙이고, 사람은 규칙이 붙인 결과를 확인합니다.

규칙이 못 찾는 경우는 사람이 붙입니다. 예를 들어 서로 다른 원인이 겹쳤거나 기록에 없는 일(수작업 조치)이 끼었을 때입니다. 이때는 붙인 사람과 시각을 같은 줄에 남깁니다. 나중에 근본 원인의 신뢰도를 사람이 붙인 줄과 규칙이 붙인 줄로 나누어 볼 수 있어야 하기 때문입니다(11절).

이어서 모든 사유 코드를 한 표에 놓습니다. 코드의 분류와 뜻은 시뮬레이터가 가진 코드 설명표를 그대로 읽은 것입니다. 오른쪽 두 열은 같은 기록을 직접 사유로 센 장수와 근본 원인으로 센 장수입니다.

4근본 원인으로 다시 그리기

같은 사건 건, 같은 잃은 장수를 이번에는 근본 원인으로 모읍니다. 합계는 달라질 수 없고(장), 장수가 어느 막대로 옮겨 가는지만 달라집니다. 막대의 값을 바꾸면 두 그림이 함께 움직입니다.

같은 기록, 두 가지 이름 — 직접 사유 파레토와 근본 원인 파레토
무엇을 볼지 먼저. 1) 두 그림의 1위가 같은 코드인지, 2) 직접 사유에서 3위 안에 들지 못하던 코드가 근본 원인에서는 몇 위인지, 3) 오른쪽 선택 상자에서 직접 사유를 바꿔 가며 그 사유의 근본 원인이 몇 개 코드로 흩어지는지 보십시오.
직접 사유
근본 원인
직접 × 근본 교차표 — 직접 사유 한 줄이 어느 근본 원인으로 나뉘는가 (유리 천 장)

버리지 않습니다. 근본 원인과 짝으로 둡니다. 직접 사유는 현장에서 무엇이 보였는지의 기록이고, 그 자리에서 사람이 바로 붙일 수 있는 이름입니다. 근본 원인은 거슬러 올라간 뒤에야 붙으므로 늦거나 비어 있을 수 있습니다. 근본 원인이 비어 있는 사건은 직접 사유 파레토에라도 남아 있어야 Loss 가 누락되지 않습니다.

다만 개선 과제를 고르는 막대는 근본 원인 쪽에서 고르고, 직접 사유 파레토는 ‘지금 라인에서 무엇이 보이는가’를 알려 주는 참고 그림으로 보고서에 같이 싣습니다(11절의 보고서 양식).

5원인이 된 블록 — 남 때문에 잃은 몫과 남에게 잃게 한 몫

블록마다 두 가지를 셉니다. 내가 잃은 것은 그 블록이 서 있던 Loss 이고, 남에게 잃게 한 것은 그 블록에서 일어난 일이 다른 블록에서 잃게 만든 Loss 입니다(원인 블록 칸으로 셉니다). 직접 사유만 보면 앞의 것만 보이므로, 앞 블록 때문에 손해를 본 뒤 블록이 개선 대상처럼 보입니다.

블록별 Loss — 잃은 것과 잃게 한 것 (유리 장수, 일)
그 블록이 다른 블록 때문에 잃은 것그 블록이 다른 블록에게 잃게 한 것

블록 단위 과제의 근거는 근본 원인 코드와 원인 블록을 같이 본 표에서 나옵니다. 아래는 (근본 원인 코드, 원인 블록) 칸을 큰 순으로 다섯 개 늘어놓은 것입니다. 이 칸 하나가 곧 ‘어느 블록의 어느 일을 고치면 얼마가 줄어드나’입니다.

6코드 체계 설계 — 합치기와 나누기

근본 원인을 붙이기로 했다면 이제 코드를 어떻게 설계하느냐가 남습니다. 같은 사건에 다른 코드 체계를 입히면 막대가 달라지고, 1위도 달라질 수 있습니다. 아래 근본 원인 파레토에서 코드를 합치거나 블록별로 쪼개 보십시오. 합계 장은 변하지 않습니다.

근본 원인 코드 체계 만지기
무엇을 볼지 먼저. 1) 설비 두 코드를 하나로 합치면 1위가 무엇이 되는지, 2) 코드를 블록별로 잘게 나누면 1위의 몫과 이름이 어떻게 되는지, 3) 기타 문턱을 올리면 기타 막대가 어디까지 커지는지 보십시오. 너무 잘게 나누면 1위가 흩어져 사라지고, 너무 크게 묶으면 어느 설비를 고칠지가 안 보입니다.

좋은 코드 체계의 점검표. 아래 여섯 가지를 코드 체계를 정하거나 바꿀 때마다 확인합니다. 마지막 칸의 값은 위 조작에 따라 함께 바뀝니다.

정해진 개수는 없고, 두 가지로 판단합니다. 하나는 기타의 몫입니다. 어느 코드에도 못 넣은 사건이 많아 기타가 커지면 코드 목록에 빠진 일이 있다는 신호이니 코드를 더하거나 나눕니다. 다른 하나는 순위의 흔들림입니다. 막대 둘의 몫이 비슷한데 기간만 바꿔도 1, 2위가 뒤바뀐다면 그 둘은 판단에 쓰기에 너무 잘게 나눈 것일 수 있습니다(7절).

또 과제의 주인이 다른 코드는 합치지 않습니다. 설비 PM 과 마스크 불량은 담당 부서와 개선 방법이 다르므로 합치면 막대는 커져도 과제는 만들 수 없습니다.

7순위 흔들림 — 한 달 파레토의 1위는 우연일 수 있습니다

  • 순위 흔들림 (rank instability) — 기간이나 표본이 바뀔 때 파레토의 순위가 우연으로 바뀌는 정도입니다. 흔들림이 크면 한 번 본 순위로 과제를 정하기 어렵습니다. 0402 에서 일치율에 구간을 붙인 것과 같은 생각으로, 순위에도 구간을 붙입니다.

같은 기록을 월요일부터 7일씩 잘라 주마다 파레토를 그립니다(주. 끝에 남는 일은 7일이 안 차서 뺍니다). 사건은 시작한 시각이 속한 주에 넣습니다. 기준으로 삼은 순위는 전체 일의 순위입니다.

시드 수와 기간의 선택: 시드 하나에 밀리초 안팎이 걸려서(이 페이지가 처음 열릴 때 잰 값) 일짜리 개를 한 번에 돌리면 화면이 얼어붙지 않도록 두 개씩 끊어 돌립니다. 기간을 줄이지 않고 기본 일을 그대로 쓴 것은 대표 기록과 같은 조건으로 견주기 위해서이고, 시드 수 는 몇 초 안에 끝나는 한도로 정했습니다. 더 많이 돌리면 구간이 조금 좁아집니다.

시드별 파레토의 순위 분포
무엇을 볼지 먼저. 1) 근본 원인에서 1위가 된 비율이 가장 높은 코드가 매 시드 1위는 아닌지, 2) 표본 시드 수를 줄이면 1위가 된 비율이 얼마나 출렁이는지, 3) 기본 시드의 1위·2위 몫 차가 분포의 어디쯤인지 보십시오.

1위가 바뀌어도 흔들림 구간 안이면 과제를 바꾸지 않습니다. 막대 둘의 몫이 비슷하면 어느 달에는 앞의 것이, 어느 달에는 뒤의 것이 1위가 됩니다. 그때마다 과제를 바꾸면 어느 것도 끝내지 못합니다. 위 7-2 의 분포에서 둘이 서로의 순위 구간 안에 있다면 둘을 한 묶음 과제로 두고, 순서는 개선하기 쉬운 쪽이나 효과를 검증하기 쉬운 쪽부터 정합니다.

반대로 몫의 차가 분포의 바깥으로 벗어난 달에는 라인에서 무슨 일이 있었는지 먼저 봅니다. 1위가 바뀐 것이 우연이 아니라 설비 교체나 제품 변경 같은 구조적 변화일 수 있기 때문입니다.

import pandas as pd

# ---- 가정·설정: 회사 값으로 바꿀 곳 --------------------------------------------------
DAYS = 60                         # 기록 기간(일)
START = pd.Timestamp("2026-01-05 00:00")   # 기록 시작 시각(월요일 0시)
N_TURN = 120                      # 챔버 한 턴이 만드는 유리 장수(챔버 한 턴 환산에 씀)
RATE = 0.30                       # 과제의 개선율(가정)
DEFAULT_SEED = 20261011           # 이 가상 공장의 기본 시드(분포 요약에서 따로 떼어 본다)
CATEGORY = {"EQ-BD": "설비", "EQ-PM": "설비", "Q-MASK": "품질", "Q-EVAP": "품질", "LG-TRANS": "물류", "LG-STK": "물류",
            "LG-CST": "물류", "LG-JC": "물류", "CL-CAPA": "세정", "JC-EARLY": "운영", "RUN-TRIPLE": "운영", "LB-LINE": "라인"}   # 사유 코드 → 분류


def fm(x):
    """천 단위 쉼표를 붙인 정수(반올림은 0.5 에서 올림)."""
    return format(int(x + 0.5 + 1e-6), ",")


# ---- 1. 불러오기와 파레토 ---------------------------------------------------------------
def load_events(path="loss_events.csv"):
    """Loss 사건 표. 시작 시각에서 기록 시작부터 몇 번째 주인지(week)도 붙인다."""
    df = pd.read_csv(path, keep_default_na=False)
    df["week"] = ((pd.to_datetime(df["start_ts"]) - START) // pd.Timedelta(days=7)).astype(int)
    return df


def pareto(df, by, value="loss_glass"):
    """by 열의 값마다 사건 수·합·몫·누적 몫. 큰 순(같으면 이름 순).
    쓰면 안 되는 때: 사유 코드 체계가 바뀐 기간의 기록을 한 표에 섞어 견줄 때."""
    g = df.groupby(by)[value].agg(["count", "sum"]).reset_index()
    g.columns = [by, "n", "value"]
    g = g.sort_values(["value", by], ascending=[False, True]).reset_index(drop=True)
    tot = g["value"].sum()
    g["share"] = g["value"] / tot
    g["cum"] = g["value"].cumsum() / tot
    return g


def crosstab_direct_root(df, value="loss_glass"):
    """행 = 직접 사유, 열 = 근본 원인, 칸 = 잃은 유리 장수. 행·열은 합이 큰 순.
    쓰면 안 되는 때: 근본 원인 칸이 비었거나 추정으로 채운 기록으로 만들 때(빈칸은 비어 있는 채로 두십시오)."""
    t = pd.crosstab(df["reason"], df["root_cause"], values=df[value], aggfunc="sum").fillna(0.0)
    return t.loc[t.sum(axis=1).sort_values(ascending=False, kind="stable").index, t.sum(axis=0).sort_values(ascending=False, kind="stable").index]


def merge_codes(df, mapping, split=(), by="root_cause", min_share=0.0, value="loss_glass"):
    """코드를 합치고(mapping: 코드 → 새 이름) 나눈 뒤(split: 블록별로 쪼갤 코드) 파레토를 다시 낸다.
    min_share 보다 작은 막대는 '기타' 하나로 묶는다. 쓰면 안 되는 때: 합친 체계로 과거 기록의 순위를 지난 체계의 순위와 견줄 때."""
    lab = df[by].map(mapping).fillna(df[by])
    for c in split:
        lab = lab.where(~((df[by] == c) & ~df[by].isin(mapping.keys())), df[by] + "@" + df["caused_by_block"])
    p = pareto(df.assign(label=lab), "label", value)
    small = p["share"] < min_share
    if min_share > 0 and small.any():
        p = pd.concat([p[~small], pd.DataFrame({"label": ["기타"], "n": [p.loc[small, "n"].sum()], "value": [p.loc[small, "value"].sum()]})], ignore_index=True)
        p["share"] = p["value"] / p["value"].sum()
        p["cum"] = p["value"].cumsum() / p["value"].sum()
    return p


def weekly_pareto(df, by, days=DAYS):
    """주마다 파레토(일곱 일이 다 찬 주만). 쓰면 안 되는 때: 한 주 사건이 수십 건 미만인 설비 한 대의 기록 — 주마다 순위가 우연으로 뒤바뀝니다."""
    return {w: pareto(df[df["week"] == w], by) for w in range(days // 7)}


# ---- 2. 순위 흔들림 ---------------------------------------------------------------------
def rank_stability(frames, by, value="loss_glass"):
    """frames: 시드(또는 기간) 하나당 표 하나. 코드마다 1위가 된 비율과 순위·몫의 분포(25·50·75%).
    쓰면 안 되는 때: 표본(시드·기간)이 서너 개뿐일 때 — 비율이 몇 개 값밖에 못 가집니다."""
    sums = [f.groupby(by)[value].sum() for f in frames]
    codes = sorted(set().union(*[set(s.index) for s in sums]))
    mat = pd.DataFrame([[s.get(c, 0.0) for c in codes] for s in sums], columns=codes)
    rk = np.zeros(mat.shape, dtype=int)
    for i, row in mat.iterrows():
        order = sorted(codes, key=lambda c: (-row[c], c))
        for j, c in enumerate(order):
            rk[i, codes.index(c)] = j + 1
    share = mat.div(mat.sum(axis=1), axis=0)
    out = pd.DataFrame({"code": codes, "top1": (rk == 1).mean(axis=0), "r25": np.quantile(rk, 0.25, axis=0), "r50": np.quantile(rk, 0.5, axis=0),
                        "r75": np.quantile(rk, 0.75, axis=0), "s50": share.median().values})
    return out.sort_values(["top1", "r50", "s50"], ascending=[False, True, False]).reset_index(drop=True)


def percentile(values, v):
    """v 가 values 안에서 몇 % 자리인가(같은 값은 반씩)."""
    x = np.asarray(values, dtype=float)
    return ((x < v - 1e-9).sum() + 0.5 * (np.abs(x - v) <= 1e-9).sum()) / len(x)


# ---- 3. 과제를 걸었을 때 고칠 수 있는 장수 -----------------------------------------------
def fixable_glass(df, rate=RATE):
    """개선율 rate 로 세 과제를 걸었을 때 줄어드는 유리 장수.
    A: 직접 사유 1위(증상)에 건 과제 — 한 과제가 닿는 곳은 그 사유의 근본 원인 하나뿐이라 가장 큰 근본 원인의 몫만 센다.
    B: 직접 사유 가운데 자기 원인(직접 사유 = 근본 원인)인 1위에 건 과제.   C: 근본 원인 1위에 건 과제.
    쓰면 안 되는 때: rate 를 근거 없이 정하고 금액으로 바로 바꿀 때 — 먼저 지난 과제의 실제 줄어든 폭을 적어 두십시오."""
    d = pareto(df, "reason")
    a_top = d.loc[0, "reason"]
    a_reach = pareto(df[df["reason"] == a_top], "root_cause").loc[0]
    selfev = df[df["reason"] == df["root_cause"]]
    b_code = pareto(selfev, "reason").loc[0, "reason"]
    b_glass = d.loc[d["reason"] == b_code, "value"].iloc[0]
    r = pareto(df, "root_cause").loc[0]
    return {"A": (a_top, a_reach["root_cause"], rate * a_reach["value"]), "B": (b_code, rate * b_glass), "C": (r["root_cause"], rate * r["value"])}

사유 코드 설계 점검표

  1. 서로 겹치지 않는가 — 한 사건이 두 코드에 동시에 들지 않고, 같은 일을 사람마다 다른 코드로 적지 않습니까.
  2. 빠짐없는가 — 모든 사건이 어떤 코드에든 들어갑니까. 기타의 몫이 5% 를 넘으면 목록을 다시 봅니다.
  3. 근본 원인 칸이 필수인가 — 비어 있는 채로 저장되는 줄이 없습니까. 직접 사유만 남은 줄은 따로 셉니다.
  4. 원인 블록 칸이 있는가 — 근본 원인이 일어난 블록을 적습니다. 같은 블록이면 자기 자신을 적습니다.
  5. 붙이는 규칙과 붙인 사람이 남는가 — 규칙으로 붙였는지 사람이 붙였는지, 붙인 시각과 함께.
  6. 판이 있는가 — 코드 체계를 바꾼 날짜가 남아 있어, 바뀐 기간끼리 순위를 견주지 않습니다.
  7. 한 코드에 한 주인이 있는가 — 코드마다 개선을 맡을 부서나 사람이 정해져 있습니다. 주인을 못 정하는 코드는 나눕니다.
