사내 데이터 파이프라인

뽑고, 잇고, 점검하고, 분석하고, 남기는 일을 정해진 시각에 사람 손 없이 되풀이하는 법

분석 함수가 맞아도 그 함수에 들어가는 표가 틀리면 결과가 조용히 틀립니다. 그래서 파이프라인은 1) 정해진 시간 창으로 자료를 뽑고, 2) glass_id·마스크·챔버 같은 키로 잇되 이벤트는 ‘챔버가 같고 시각이 구간 안’으로 붙이고, 3) 매 실행마다 행 수·키 중복·열 구성·빈칸 비율·이음 비율·시각 범위·모델 판의 일곱 규칙으로 점검해 통과할 때만 결과를 내고(늦게 온 자료는 점검과 별개로 알림만 줍니다), 4) 같은 입력이면 언제 다시 돌려도 같은 결과(입력 지문·코드 판·출력 지문)가 나오게 만듭니다. 그래야 에이전트가 이 결과 위에서 판단할 수 있습니다.

시작하기 전에

이미 아시는 것 — 0101의 FDC 요약값, 0201의 궤적에서 특징 뽑기, 0206의 상태·전이·사례 기록(links·trace), 0302의 계수 표, 0303의 join_fdc_ppa(못 이은 행 수)와 온도 보정, 0305의 모델 판·센서 판·드리프트 감시. 표·열·행과 CSV 파일.

  • FDC 요약값 (0101)
  • 궤적 → 특징 (0201)
  • 사례 기록 · links (0206)
  • 계수 표 (0302)
  • FDC·PPA 잇기 · 온도 보정 (0303)
  • 모델 판 · 센서 판 · 드리프트 감시 (0305)

새로 이름을 붙이는 낱말은 여섯 개입니다. 쓰이는 자리에서 하나씩 정의하고, 정의한 뜻 그대로만 씁니다. 이 여섯 개 말고 계산에 붙인 이름(되돌아보기 창 · 늦게 온 자료 · 점검 문턱 · 실행 기록)은 쓰는 자리에서 문장으로 정의합니다. SQL 의 핵심 네 마디(SELECT · WHERE · JOIN · GROUP BY)와 집계 함수 COUNT · AVG · SUM, 정렬 ORDER BY, 구간 BETWEEN 은 처음 쓰는 자리에서 한 줄로 풀어 둡니다.

  • 파이프라인 (pipeline)
  • 시간 창 (time window)
  • 구간 이음 (interval join)
  • 자료 점검 (data check)
  • 지문 (fingerprint)
  • 멱등 (idempotent)

이 실험실에서 가져가는 것

  1. 실무에서 쓰는 곳 — 0101~0306의 분석을 매일 손으로 엑셀에 붙이는 대신, 사내 DB에서 뽑아 키로 잇고 정해진 시각에 돌려 결과를 남기는 일. 에이전트가 쓸 ‘데이터 손발’입니다(2~8절).
  2. 손으로 연습 — 시간 창을 밀어 보며 두 번 세거나 빠뜨리는 줄을 세고(3절), 이벤트를 유리에 붙이고(4절), 점검 문턱을 옮겨 14일 모의 운전에서 일부러 넣은 고장을 잡아 보고(5절), 되돌아보기 창의 길이를 옮기고(6절), 같은 날을 다시 돌려 지문을 견줍니다(7절).
  3. 다음 날 산출물 — load_db·extract·join_keys·attach_events·run_checks·run_daily Python 함수(sqlite3 표준 라이브러리, 10절)와 파이프라인 실행 기록지(11절), 작업 스케줄러 등록 예(8절).
  4. 기록할 데이터 — 실행마다 입력 범위·행 수·입력 지문·코드 판·점검 결과·출력 지문(11절).
  5. 사람·규칙·에이전트의 몫 — 문턱 승인·실패 알림 처리·스키마 변경 공지는 사람, 점검과 재실행 조건은 규칙, 뽑기·잇기·분석·보고 초안·실패 요약은 에이전트(8절).
  6. 성과 환산 — 손으로 붙이던 시간과, 점검이 막은 ‘틀린 보고’ 일수(9절).

여기서부터 위 모의 운전을 이용한 풀이입니다

1손에 쥔 것 — 사내 시스템이 내놓는 표 네 장

가상 공장은 블록 B02·B03의 챔버 1~4, 곧 개 챔버입니다. 유리는 챔버마다 분에 한 장씩 증착하고, 턴(장)이 되풀이됩니다. 모든 유리를 적으면 표가 너무 커지므로, FDC 는 턴 안 순번을 으로 나눈 나머지가 인 유리(5·15·…·115번)를 표본으로 적재하고, PPA 는 그 가운데 턴마다 장(번)만 잽니다. PPA 표의 ppa_metric 은 0301 의 지표(|평균| + 3σ)를 dx 와 dy 각각 구해 큰 쪽입니다(0304 는 dx 만 썼지만 이 가상 공장 표는 둘 중 큰 쪽을 쓰는 약속입니다). 아래 네 장이 사내 DB 가 실제로 받은 모습입니다(가상 이름).

표 두 장의 앞부분을 보면 이렇습니다. glass_id 가 두 표를 잇는 키이고, ts 는 유리를 증착한 시각, measured_ts 는 PPA 를 잰 시각입니다. 측정은 증착한 뒤에 합니다(분포 가정: 증착 뒤 분 + 평균 분의 지수 분포 지연).

실행은 하루 한 번, 매일 아침 6시입니다. 실행 k 일째는 전날 6시부터 당일 6시까지의 자료를 다룹니다. 보고 날짜는 그 창이 시작한 날짜로 부릅니다.

2첫 시도 — 네 표를 그대로 이어 14일을 돌려 보기

0303의 분석을 그대로 부릅니다. 챔버마다 하루 동안의 유리에서 M̂x − (열 기울기) × (FDC 온도 − °C) 를 평균하고(열 기울기 ppm/K 는 0303 에서 구한 값), 그날의 PPA 지표가 한계 µm(정답본 지표의 90 백분위, 가정)를 넘은 유리를 셉니다. 점검 없이, 들어온 표를 그대로 이어서 일을 돌린 결과입니다.

점검 없이 낸 결과 — 챔버 8개의 보정 후 Mx 평균 (ppm)
무엇을 볼지 먼저. 1) 먼저 단추를 누르지 말고 선만 보십시오. 어느 날이 틀렸는지 가릴 수 있는지 스스로 물어보십시오. 2) 그다음 ‘정답 겹쳐 보기’를 눌러, 고장 없는 자료로 돌린 정답(점선)과 달라진 날(붉은 띠)이 어디인지 보십시오. 3) 결과만 봐서는 구분이 되지 않던 날이 몇 일이었는지 세어 보십시오.
점검 없이 낸 결과(챔버마다 한 줄)정답(고장 없는 자료)정답과 달라진 날

여기서 막힙니다. 정답을 겹쳐 보기 전에는 어느 날이 틀렸는지 결과만으로는 가를 수 없습니다. 값이 튄 날이 있어도 그것이 고장 때문인지 공정이 실제로 바뀐 것인지(0101 의 PM 뒤 이동처럼) 알 수 없기 때문입니다. 현장에는 정답이 없습니다. 그러니 결과가 아니라 결과가 나오기 전의 표를 보는 방법이 필요합니다. 먼저 이 일 전체에 이름을 붙이고, 자료를 어떻게 자르고 잇는지부터 짚습니다.

엑셀로 하는 일이 틀려서가 아니라, 틀린 날을 알아볼 방법이 없기 때문입니다. 이 모의 운전에서 점검 없이 낸 결과는 일이 정답과 달랐는데, 그 가운데 열 이름이 바뀌어 칸이 비었던 날을 빼면, 값이 튀어 보여도 고장 때문인지 공정이 바뀐 것인지 눈으로는 가려지지 않습니다.

손으로 붙이는 사람도 같은 표를 받으니 같은 고장을 만납니다. 다만 사람은 그날 이상하다고 느낀 것을 기억에만 남기고, 몇 달 뒤에는 ‘언제부터 자료가 이상했나’를 답할 기록이 없습니다. 파이프라인은 같은 일을 하되 점검과 실행 기록을 남깁니다.

3이름 — 파이프라인과 시간 창, 그리고 SQL 네 마디

  • 파이프라인 (pipeline) — 뽑기 → 잇기 → 점검 → 분석 → 남기기를 정해진 순서로 묶어, 사람이 손대지 않고 되풀이해 돌리는 작업입니다. 어느 칸이든 실패하면 그 뒤 칸으로 넘어가지 않습니다.
  • 시간 창 (time window) — 한 번의 실행이 다루는 자료의 시작·끝 시각입니다. 창이 겹치거나 비면 같은 유리를 두 번 세거나 빠뜨립니다. 이 실험실의 창은 [시작, 끝) 로, 시작은 포함하고 끝은 포함하지 않습니다.

사내 DB 에서 표를 꺼내는 공통어가 SQL 입니다. 이 실험실의 핵심은 네 마디입니다. SELECT 는 어떤 열을 꺼낼지, WHERE 는 어떤 줄만 남길지(여기서는 시간 창으로 자르기), JOIN 은 키가 같은 줄끼리 옆으로 붙이기, GROUP BY 는 같은 값끼리 묶어 계산하기입니다. 여기에 집계 함수 COUNT(줄 수 세기)·SUM(합)·AVG(평균)와 ORDER BY(정렬)가 곁들여집니다. 아래 글은 보여 주는 글입니다. 10절의 Python 은 같은 SQL 을 sqlite3 로 실제로 돌려 같은 숫자를 냅니다.

SELECT * FROM fdc_glass WHERE ts >= :s AND ts < :e
SELECT * FROM ppa_coef WHERE ts >= :s AND ts < :e AND measured_ts <= :a

위 둘이 ‘뽑기’입니다. :s 는 창 시작, :e 는 창 끝, :a 는 실행 시각(이 시각까지 도착한 PPA 만 봅니다). 이어서 ‘잇기’와 챔버별 집계입니다.

SELECT f.block || '-' || f.chamber AS chamber_key,
       COUNT(f.chamber_temp)                                  AS n,
       AVG(p.Mx - :slope * (f.chamber_temp - :t0))            AS mx_comp,
       COALESCE(SUM(p.ppa_metric > :spec), 0)                 AS n_exceed
FROM fdc_glass f JOIN ppa_coef p ON p.glass_id = f.glass_id
WHERE f.ts >= :s AND f.ts < :e AND p.ts >= :s AND p.ts < :e AND p.measured_ts <= :a
GROUP BY f.block, f.chamber ORDER BY f.block, f.chamber

AVG 는 빈칸(NULL)을 건너뛰고 평균하므로, FDC 온도가 비어 있는 유리는 보정할 수 없어 평균에서 빠집니다(0303 과 같은 규칙).

뽑기와 잇기는 사내 DB 와 말하는 공통어가 SQL 이라 최소한은 알아야 하고, 분석은 Python 에 맡겨 나눠 쓰면 됩니다. 이 실험실에서 쓴 핵심은 SELECT · WHERE · JOIN · GROUP BY 네 마디이고, 아래 화면의 챔버별 표는 그 네 마디가 한 번에 돌려주는 표 한 장입니다.

SQL 문장은 AI 가 대신 써 줄 수 있지만, 창의 끝을 포함하는지(< 인지 <= 인지)와 JOIN 키가 맞는지는 사람이 읽고 확인해야 합니다. 같은 유리를 두 번 세는 일이 바로 그 자리에서 생깁니다(3절 슬라이더).

하루치 실행 한 번 — 창을 자르고, 잇고, 챔버별로 묶기
무엇을 볼지 먼저. 1) 날짜를 바꿔 가며 뽑힌 FDC 줄 수와 PPA 줄 수가 얼마나 일정한지 보십시오. 2) 표의 챔버별 숫자가 위 SQL 한 번이 돌려주는 결과입니다. 3) 아래 슬라이더로 창 시작을 밀면, 어제 창과 겹쳐 두 번 세는 줄이나 어느 창에도 안 든 줄이 생깁니다.

4구간 이음 — 이벤트를 유리에 붙이기

glass_id 로 잇는 것은 같은 유리를 두 표에서 찾는 일이라 키가 같으면 됩니다. 이벤트(PM · 세정 · 센서 교정 · 인터락)는 다릅니다. 이벤트에는 유리 번호가 없고 시작·끝 시각만 있으니, 어느 유리가 그 이벤트 동안 증착됐는지는 시각으로 찾아야 합니다. 이 이름이 필요합니다.

  • 구간 이음 (interval join) — 키가 같고, 한쪽의 시각이 다른 쪽의 시작~끝 구간 안에 들 때 잇는 것입니다. 여기서는 챔버가 같고 유리의 ts 가 이벤트의 start_ts 와 end_ts 사이(양 끝 포함)일 때 그 유리에 이벤트를 붙입니다. 이 실험실의 이벤트 구간은 ‘그 이벤트가 FDC 값에 영향을 준다고 기록한 구간’입니다.
SELECT COUNT(DISTINCT f.glass_id) FROM fdc_glass f
JOIN events e ON e.block = f.block AND e.chamber = f.chamber AND f.ts BETWEEN e.start_ts AND e.end_ts
WHERE f.ts >= :s AND f.ts < :e

여기서 BETWEEN 은 값이 두 끝 사이(양 끝 포함)에 드는 줄만 고르고, DISTINCT 는 같은 유리가 여러 번 나와도 한 번만 세게 합니다.

세정·센서 교정 뒤에 증착된 유리를 이렇게 표시해 두면, 0303 의 열변형·0305 의 센서 판 이야기가 바로 이어집니다. 어느 유리가 교정 직후였는지가 표에 있기 때문입니다.

고른 날의 챔버별 시간 축 — 이벤트 띠와 유리 점
무엇을 볼지 먼저. 1) 이벤트 띠 안의 점만 색이 칠해지는지 보십시오. 2) 시각대가 어긋난 날(아래 단추)에서 ‘적재본의 ts’와 ‘정답본의 ts’를 번갈아 보며, 같은 유리가 다른 이벤트에 붙거나 아무 데도 안 붙는 것을 보십시오. 3) 붙은 유리 수가 얼마나 달라지는지 아래 표에서 보십시오.

5자료 점검 — 결과가 나오기 전에 표를 보기

2절에서 막힌 이유는 결과만 봤기 때문입니다. 결과가 나오기 전의 표가 약속대로 왔는지는 규칙으로 볼 수 있습니다. 이 일에 이름을 붙입니다.

  • 자료 점검 (data check) — 분석 전에 표가 약속대로 왔는지 보는 규칙입니다(행 수 · 키 중복 · 열 구성 · 빈칸 비율 · 이음 비율 · 시각 범위 · 모델 판의 일곱 규칙). 한 규칙이라도 실패하면 결과를 내지 않고 알립니다.

점검 규칙은 아래 일곱 가지이고, 문턱(점검 문턱, 통과와 실패를 가르는 값)은 가운데 세 가지가 조절 가능합니다. 나머지 넷은 0이어야 하거나 하나여야 하는 규칙이라 문턱을 두지 않습니다.

규칙보는 것실패하면
rows 행 수FDC·PPA 줄 수가 지난 번 실행의 중앙값의 몇 배인가 (문턱: 하한)빠진 자료 또는 늦게 온 자료
dup 키 중복같은 glass_id 가 한 표에 두 번 있는 줄 수 (0이어야 함)같은 유리를 두 번 셉니다
cols 필수 열 존재필수 열 가운데 한 줄도 값이 없는 열의 수 (0이어야 함)열 이름이 바뀌었거나 열이 사라짐
blank 빈칸 비율chamber_temp 가 빈 줄의 비율 (문턱: 상한)온도를 못 써서 보정이 빠집니다
join 이음 비율PPA 줄 가운데 FDC 줄과 이어진 비율 (문턱: 하한)FDC 가 빠졌거나 시각이 어긋남
ts ts 범위·순서창 밖 줄 수 + 증착 시각이 측정 시각보다 늦은 줄 수 (0이어야 함, 증착이 측정보다 늦을 수 없음)시각대가 어긋남
model 모델 판PPA 표의 model_ver 가 몇 종류인가 (1이어야 함)계수를 만든 모델이 섞임

여덟째는 점검이 아니라 알림입니다. 늦게 온 자료란 자기 날 창의 끝(06시)을 지나서 도착한 PPA 줄이고, 지난 실행 뒤에 도착한 이전 날 줄 수를 세어, 되돌아보기 재집계가 필요하다는 신호를 줍니다. 오늘 결과를 막지는 않습니다. 6절에서 다룹니다.

고른 날의 점검 표와 14일 달력
무엇을 볼지 먼저. 1) 달력에서 날짜를 눌러 그날의 점검 값이 어느 규칙에서 갈리는지 보십시오. 2) 문턱을 엄격하게 옮기면 붉은 날이 늘고 ‘고장 없는 날의 실패’(헛잡음)가 생기는지, 느슨하게 옮기면 ‘고장이 있는데 통과’(놓침)가 생기는지 보십시오. 3) 맨 아래 표에서 어느 고장을 어느 규칙이 잡는지 보십시오.
고장 글자: 늦 = 늦게 온 자료 · 중 = 중복 행 · 빠 = 빠진 구간 · 열 = 열 이름 바뀜 · 시 = 시각대 어긋남 · 모 = 모델 판 섞임 · 칸이 좁으면 통 = 통과 · 실 = 실패 · 같 = 같음 · 다 = 다름

지난 실행 기록의 분포로 정하고, 헛잡음의 비용과 놓침의 비용을 맞바꿔 고릅니다. 행 수 하한은 고장 없는 날의 행 수가 지난 중앙값의 몇 배까지 흔들리는지(이 모의 운전에서는 ~ 배)를 보고, 그 바깥에 문턱을 둡니다.

문턱을 빡빡하게 두면 정상인 날도 알림이 와서 사람이 매번 들여다봐야 합니다(헛잡음). 느슨하게 두면 고장 난 표가 통과합니다(놓침). 0202 에서 1종·2종 오류를 맞바꾼 것과 같은 일이며, 어느 쪽 비용이 큰지는 현장이 정합니다. 문턱은 사람이 승인하고, 승인한 값과 날짜를 실행 기록에 남깁니다.

6늦게 온 자료와 되돌아보기 창

PPA 는 증착한 뒤에 재니, 06시 실행 시점에는 마지막 몇 시간치가 아직 안 온 채로 계산됩니다. 며칠 늦게 들어오는 줄도 있습니다. 그래서 실행 때 어제와 그제도 다시 집계해 늦게 온 줄을 반영합니다. 이 ‘다시 집계하는 날 수’를 되돌아보기 창이라 부릅니다. 길수록 많이 바로잡지만 매번 다시 돌리는 양이 늘어납니다.

PPA 줄이 창 끝(06시)을 지나 얼마 뒤에 도착했는가
무엇을 볼지 먼저. 1) 첫 막대(0~6시간)가 압도적으로 큰 것을 보십시오. 보통의 측정 지연이 06시 경계를 넘는 줄입니다. 2) 24시간 이상 늦은 막대는 고장으로 들어간 줄입니다. 3) 되돌아보기 창을 늘리면 파란 선이 오른쪽으로 가며 바로잡히는 줄이 늘고, 다시 돌리는 일수도 같이 늘어나는 것을 보십시오.
되돌아보기 창 안에 도착(바로잡힘)창을 넘어 도착(못 바로잡음)창의 끝

7지문과 멱등 — 같은 입력이면 같은 결과

에이전트가 이 결과 위에서 판단하려면, 결과가 어느 입력에서 나왔는지를 짧게 증명할 수 있어야 합니다. 이름 두 개가 필요합니다.

  • 지문 (fingerprint) — 입력 자료나 출력 결과를 정해진 방식으로 줄인 짧은 문자열(해시)입니다. 다르면 반드시 무언가 바뀐 것이고, 같으면 같은 자료일 가능성이 매우 높습니다(우연히 같아지는 충돌은 드물지만 있을 수 있습니다). 이 실험실은 줄을 glass_id 순으로 정렬해 이은 글자에 FNV-1a 32비트 해시를 씁니다(보안용이 아니라 ‘같은 자료인가’ 확인용이어서 단순한 해시로 충분합니다).
  • 멱등 (idempotent) — 같은 날짜로 몇 번을 다시 돌려도 결과 표가 한 벌만 남고 내용이 같은 성질입니다. 덮어쓰기 키는 보고 날짜(run_date)입니다.

한 번 돌릴 때마다 한 줄씩 남기는 실행 기록(보고 날짜 · 시간 창 · 행 수 · 지문 · 코드 판 · 점검 결과 · 알림 · 사유)이 이 지문들을 담는 그릇입니다. 0206 의 사례 기록이 links 로 이벤트와 턴을 가리켰듯, 실행 기록은 입력 표의 범위와 지문을 가리킵니다. 이 이름들을 확인하는 방법은 단추 두 개입니다. 같은 날 다시 돌리기는 입력이 그대로이니 지문도 결과도 같고 결과 표는 여전히 한 벌이어야 합니다. 늦은 자료가 들어온 뒤 다시 돌리기는 입력이 바뀌었으니 지문이 달라지고, 무엇이 바뀌었는지가 보여야 합니다. 두 번째는 6절의 되돌아보기 창(지금 일)만큼 뒤의 시각 기준으로 돌립니다.

실행 기록 — 한 번 돌릴 때마다 한 줄
무엇을 볼지 먼저. 1) 같은 날을 두 번 돌리면 지문이 그대로이고 ‘저장된 결과 표’가 한 벌인지 보십시오. 2) 늦은 자료가 들어온 뒤 돌리면 입력 지문이 바뀌고 PPA 행 수가 늘어나는지 보십시오. 3) 점검에 실패한 날은 결과 대신 알림이 한 건 남는지 보십시오.

실행 기록의 입력 지문과 행 수부터 봅니다. 알림에는 어느 규칙이 실패했는지가 적혀 있으니, 먼저 그 규칙의 값(행 수 비율 · 중복 건수 · 빈칸 비율 …)을 지난 실행의 기록과 나란히 놓습니다.

입력 지문이 지난 실행과 같은 범위에서 갑자기 달라졌다면 입력 표가 바뀐 것이고, 같은 입력인데 출력 지문이 다르면 코드 판이 바뀐 것입니다. 이 순서로 보면 ‘표가 이상한가, 코드가 이상한가’를 가르는 데 몇 분이면 됩니다. 원인이 스키마 변경이면 변경 공지와 날짜를 기록에 덧붙입니다.

10Python — 회사 PC에 가져갈 코드

아래 코드는 표준 라이브러리 sqlite3 와 pandas 만 씁니다. 입력은 네 표의 CSV 와 정답 표(s15_faults.csv, 어느 날 무슨 고장이 들었는가)이고, 코드와 같은 폴더에 두면 그대로 돌아갑니다. 회사 DB 에서는 load_db 대신 읽기 전용 사본에 연결하는 함수를 같은 이름으로 바꿔 끼우면 됩니다. 각 함수에 ‘쓰면 안 되는 때’를 적었고, 맨 아래 __main__ 은 14일을 차례로 돌려 보는 예입니다. 코드 맨 위의 SCHEMA 가 schema.sql 입니다.

위 단추로 CSV 파일을 내려받을 수 있습니다.
import os, sqlite3, statistics
from datetime import datetime, timedelta
import pandas as pd

# ---- 가정·설정: 현장 값으로 바꿀 곳 ------------------------------------------------
SLOPE = -1.975908993542295               # 0303 에서 구한 열 기울기 (ppm/K)
T_REF = 80                # 기준 온도 (°C)
SPEC = 5.712791                 # PPA 지표 한계 (µm): 이보다 크면 '초과'
RULES = {"rows_min": 0.8, "blank_max": 0.02, "join_min": 0.98}   # 점검 문턱
HIST = 7                 # 행 수 기준 = 지난 이만큼 실행의 중앙값
LOOKBACK = 3             # 되돌아보기 창 (일)
CODE_VER = "pipe-1.0"        # 코드 판
T0 = datetime(2026, 3, 2, 6, 0)  # 첫 시간 창의 시작 (가상 공장의 첫 날 06:00)

SCHEMA = """
CREATE TABLE fdc_glass (glass_id TEXT, ts TEXT, block TEXT, chamber TEXT, mask_id TEXT, turn INTEGER, glass_in_turn INTEGER,
                        chamber_temp REAL, ch_temp REAL, p_steady_mean REAL, rate REAL);
CREATE TABLE ppa_coef  (glass_id TEXT, ts TEXT, measured_ts TEXT, Tx REAL, Ty REAL, theta REAL, Mx REAL, My REAL, K REAL,
                        model_ver TEXT, ppa_metric REAL);
CREATE TABLE events    (event_id TEXT, block TEXT, chamber TEXT, start_ts TEXT, end_ts TEXT, kind TEXT);
CREATE TABLE mask_hist (mask_id TEXT, from_ts TEXT, to_ts TEXT, chamber TEXT, block TEXT, state TEXT);
CREATE INDEX i_f ON fdc_glass(ts); CREATE INDEX i_g ON fdc_glass(glass_id); CREATE INDEX i_p ON ppa_coef(ts); CREATE INDEX i_q ON ppa_coef(glass_id);
"""
SQL_FDC = "SELECT * FROM fdc_glass WHERE ts >= :s AND ts < :e"
SQL_PPA = "SELECT * FROM ppa_coef WHERE ts >= :s AND ts < :e AND measured_ts <= :a"
SQL_DAILY = """
SELECT f.block || '-' || f.chamber AS chamber_key,
       COUNT(f.chamber_temp)                                  AS n,
       AVG(p.Mx - :slope * (f.chamber_temp - :t0))            AS mx_comp,
       COALESCE(SUM(p.ppa_metric > :spec), 0)                 AS n_exceed
FROM fdc_glass f JOIN ppa_coef p ON p.glass_id = f.glass_id
WHERE f.ts >= :s AND f.ts < :e AND p.ts >= :s AND p.ts < :e AND p.measured_ts <= :a
GROUP BY f.block, f.chamber ORDER BY f.block, f.chamber"""
SQL_EVENTS = """
SELECT COUNT(DISTINCT f.glass_id) FROM fdc_glass f
JOIN events e ON e.block = f.block AND e.chamber = f.chamber AND f.ts BETWEEN e.start_ts AND e.end_ts
WHERE f.ts >= :s AND f.ts < :e"""
CHAMBERS = [b + "-CH" + str(c) for b in ("B02", "B03") for c in (1, 2, 3, 4)]


def window(day):
    """day 번째 실행(1~)의 시간 창 [시작, 끝) 문자열. 끝 = 실행 시각."""
    f = lambda d: (T0 + timedelta(days=d)).strftime("%Y-%m-%d %H:%M")
    return f(day - 1), f(day)


def load_db(csv_dir):
    """네 표의 CSV 를 메모리 sqlite 에 올립니다. 쓰면 안 되는 때: 운영 DB 에 직접 대고 이 함수를 돌리지 마십시오(읽기 전용 사본에서)."""
    con = sqlite3.connect(":memory:")
    con.executescript(SCHEMA)
    for t in ("fdc_glass", "ppa_coef", "events", "mask_hist"):
        pd.read_csv(os.path.join(csv_dir, "s15_" + t + ".csv")).to_sql(t, con, if_exists="append", index=False)
    return con


def extract(con, start, end, asof):
    """뽑기: 시간 창 안의 FDC 줄과, 그 창의 PPA 줄 가운데 asof 까지 도착한 것."""
    p = {"s": start, "e": end, "a": asof}
    return con.execute(SQL_FDC, p).fetchall(), con.execute(SQL_PPA, p).fetchall()


def join_keys(con, start, end, asof):
    """잇기 + 챔버별 집계: glass_id 로 FDC 와 PPA 를 잇고, 온도를 보정한 Mx 평균과 지표 초과 건수를 챔버별로 셉니다."""
    p = {"s": start, "e": end, "a": asof, "slope": SLOPE, "t0": T_REF, "spec": SPEC}
    got = {r[0]: r for r in con.execute(SQL_DAILY, p).fetchall()}
    return [got.get(k, (k, 0, None, 0)) for k in CHAMBERS]


def attach_events(con, start, end):
    """구간 이음: 챔버가 같고 유리의 ts 가 이벤트의 start~end 안인 유리 수."""
    return con.execute(SQL_EVENTS, {"s": start, "e": end}).fetchone()[0]


def run_checks(con, fdc, ppa, start, end, asof, hist):
    """자료 점검: 규칙마다 (이름, 값, 문턱, 통과 여부). hist = 지난 실행들의 (FDC 행 수, PPA 행 수)."""
    p = {"s": start, "e": end, "a": asof}
    nf, npp = len(fdc), len(ppa)
    out = []
    if hist:
        ratio = min(nf / statistics.median(h[0] for h in hist), npp / statistics.median(h[1] for h in hist))
        out.append(("rows", ratio, RULES["rows_min"], ratio >= RULES["rows_min"]))
    else:
        out.append(("rows", None, RULES["rows_min"], True))
    dup = (nf - len({r[0] for r in fdc})) + (npp - len({r[0] for r in ppa}))
    out.append(("dup", dup, 0, dup == 0))
    empty = sum(con.execute(f"SELECT COUNT({c}) FROM fdc_glass WHERE ts >= :s AND ts < :e", p).fetchone()[0] == 0
                for c in ("glass_id", "ts", "chamber", "mask_id", "chamber_temp"))
    out.append(("cols", empty, 0, empty == 0))
    blank = 1.0 if nf == 0 else sum(r[7] is None for r in fdc) / nf
    out.append(("blank", blank, RULES["blank_max"], blank <= RULES["blank_max"]))
    ids = {r[0] for r in fdc}
    jr = 0.0 if npp == 0 else sum(r[0] in ids for r in ppa) / npp
    out.append(("join", jr, RULES["join_min"], jr >= RULES["join_min"]))
    bad = con.execute("""SELECT COUNT(*) FROM fdc_glass f JOIN ppa_coef p ON p.glass_id = f.glass_id
                         WHERE f.ts >= :s AND f.ts < :e AND p.ts >= :s AND p.ts < :e AND p.measured_ts <= :a
                           AND f.ts > p.measured_ts""", p).fetchone()[0]
    out.append(("ts", bad, 0, bad == 0))
    nv = len({r[9] for r in ppa})
    out.append(("model", nv, 1, nv <= 1))
    return out


def late_notice(con, start, asof):
    """알림(결과를 막지 않음): 지난 실행 뒤에 도착한 이전 날 PPA 줄 수 → 되돌아보기 재집계를 부르는 신호."""
    lo = (datetime.strptime(start, "%Y-%m-%d %H:%M") - timedelta(days=LOOKBACK)).strftime("%Y-%m-%d %H:%M")
    return con.execute("SELECT COUNT(*) FROM ppa_coef WHERE ts < :s AND ts >= :lo AND measured_ts > :s AND measured_ts <= :a",
                       {"s": start, "lo": lo, "a": asof}).fetchone()[0]


def fnv1a(text):
    """지문: FNV-1a 32비트 해시를 8자리 16진수로. (단순한 결정적 해시 — 보안용이 아니라 '같은 자료인가' 확인용)"""
    h = 2166136261
    for ch in text:
        h = ((h ^ ord(ch)) * 16777619) & 0xFFFFFFFF
    return format(h, "08x")


def canon(v, d):
    if v is None or v != v:
        return ""
    if isinstance(v, str):
        return v
    if isinstance(v, int):
        return str(v)
    s = f"{v:.{d}f}"
    return s[1:] if s.startswith("-") and float(s) == 0 else s


def fingerprint(fdc, ppa):
    """입력 지문: 두 표의 줄을 glass_id 순으로 정렬해 한 문자열로 잇고 해시."""
    a = sorted(fdc, key=lambda r: (r[0], r[1]))
    b = sorted(ppa, key=lambda r: (r[0], r[2]))
    la = ["|".join([r[0], r[1], r[2], r[3], r[4], str(r[5]), str(r[6]), canon(r[7], 4), canon(r[8], 4), canon(r[9], 3), canon(r[10], 4)]) for r in a]
    lb = ["|".join([r[0], r[1], r[2]] + [canon(x, 6) for x in r[3:9]] + [r[9], canon(r[10], 6)]) for r in b]
    return fnv1a("\n".join(la) + "\n#\n" + "\n".join(lb))


def out_fingerprint(daily, n_event):
    lines = [f"{k}|{n}|{canon(m, 6)}|{int(x)}" for k, n, m, x in daily] + [f"events|{n_event}"]
    return fnv1a("\n".join(lines))


def run_daily(con, day, out_dir, asof_day=None, reason="정기"):
    """하루치를 뽑고 → 잇고 → 점검하고 → 통과하면 결과 표를 남깁니다. 같은 날을 몇 번 돌려도 결과 표는 한 벌(run_date 키로 덮어쓰기).
    실행 기록은 runs.csv 에 한 줄씩 쌓고, 점검에 실패하면 결과 대신 알림 파일을 남깁니다."""
    os.makedirs(out_dir, exist_ok=True)
    s, e = window(day)
    a = window(asof_day or day)[1]
    runs_path = os.path.join(out_dir, "runs.csv")
    run_date = s[:10]
    runs = pd.read_csv(runs_path) if os.path.exists(runs_path) else pd.DataFrame()
    prev = runs if runs.empty else runs[(runs.reason == "정기") & (runs.run_date < run_date)]
    hist = [] if prev.empty else [(r.n_fdc, r.n_ppa) for r in prev.tail(HIST).itertuples()]
    fdc, ppa = extract(con, s, e, a)
    checks = run_checks(con, fdc, ppa, s, e, a, hist)
    failed = [c[0] for c in checks if not c[3]]
    rec = {"run_date": run_date, "window": f"{s}~{e}", "asof": a, "n_fdc": len(fdc), "n_ppa": len(ppa), "in_fp": fingerprint(fdc, ppa),
           "code_ver": CODE_VER, "failed_rules": "+".join(failed) or "-", "out_fp": "-", "alert": bool(failed), "reason": reason, "late_notice": late_notice(con, s, a)}
    result_path = os.path.join(out_dir, f"result_{run_date}.csv")
    if failed:
        with open(os.path.join(out_dir, f"ALERT_{run_date}.txt"), "w", encoding="utf-8") as f:
            f.write(f"{run_date} 점검 실패: {', '.join(failed)}\n결과를 내지 않았습니다. 입력 지문 {rec['in_fp']}, 행 수 FDC {len(fdc)} / PPA {len(ppa)}\n")
        if os.path.exists(result_path):
            os.remove(result_path)
    else:
        daily = join_keys(con, s, e, a)
        n_ev = attach_events(con, s, e)
        df = pd.DataFrame(daily, columns=["chamber_key", "n", "mx_comp", "n_exceed"])
        df["events_attached"] = n_ev
        df.to_csv(result_path, index=False)                  # 같은 날이면 덮어씀 = 멱등
        rec["out_fp"] = out_fingerprint(daily, n_ev)
    pd.concat([runs, pd.DataFrame([rec])], ignore_index=True).to_csv(runs_path, index=False)
    return rec, checks
